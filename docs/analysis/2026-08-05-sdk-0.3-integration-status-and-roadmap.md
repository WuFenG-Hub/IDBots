## 3. New opportunities found during implementation (not in original doc)

### Tier 1 — quick wins (small effort, clear value)

- **In-process TS hooks** (31 events, currently only PreToolUse is used) — candidate next: `PostToolUse` audit logging, `MessageDisplay` redaction, `PostCompact` persistence sync.
- **`betas: ['context-1m-2025-08-07']`** — 1M context for Sonnet 4/4.5; one-line option.

### Tier 2 — product-level features

- **Session forking / rewind** (same as original #7 above).
- **Dynamic MCP lifecycle** — `Query.setMcpServers()` / `reconnectMcpServer()` / `toggleMcpServer()` / `mcp_call` (invoke MCP tool without a model turn, staged file lanes).
- **Structured output** — `options.outputFormat: {type:'json_schema', schema}` for machine-parseable results.
- **Background task management** — `Query.backgroundTasks()` / `stopTask()` + task events.
- **`set_permission_mode` mid-session** — covered by multi-mode permissions (#7), but the SDK-side `Query.setPermissionMode()` call is not yet issued (we only switch our own `canUseTool` mode).

### Tier 3 — watch / decide per use case

- **Skill hot-reload** — `Query.reloadSkills()`; requires migrating from static system-prompt text to SDK native skills first.
- **`onUserDialog` / `onElicitation`** — structured host-rendered dialogs and MCP elicitation.
- **`applyFlagSettings` / `reinitialize`** — dynamic mid-session reconfiguration and transport-gap recovery.
- **`SDKRateLimitEvent` / `SDKPermissionDeniedMessage` / `SDKConversationResetMessage`** — events currently dropped; could surface in UI.
- **Capability tokens** (`capabilities?` on init) — feature-detect instead of version-sniffing.

## 4. Deliberately deferred (do not adopt)

- **CLI-native sandbox** — IDBots has its own QEMU micro-VM sandbox; SDK sandbox is Linux-container-oriented.
- **`SessionStore` mirroring** — duplicates IDBots' SQLite `CoworkStore`.
- **`startup()` WarmQuery** — single-use + fixed options; incompatible with multi-provider per-session env.
- **`taskBudget` (alpha)** — provider-dependent.

## 5. Known limitations of current implementation (future work)

- Auto-approve rules are persisted app-wide (not per-session); per-session overrides are in-memory only.
- Sandbox mode guest `canUseTool` (`sandbox/agent-runner/index.js`) does NOT honor auto-approve rules / permission modes / effort overrides — the guest has its own decision logic that must be updated in parallel.
- Permission mode + effort changes apply immediately in local mode; sandbox applies on next turn (guest reads stored config on resume).
- `getContextUsage()` real usage is local-mode only; sandbox uses the estimator.
